# 企划集：目录规范、素材使用与 ASK 协同实施规划

日期：2026-11-09。状态：**P1–P6 已实施并完成本地模拟验证，尚未提交、推送或部署；真实企划体验待验。**

本文保留用户需求、五项决定、实施前基底及阶段验收记录。原方案中的 `outputs/` 已取消。现行目录结构、面板和素材交接统一维护于[企划集与外部协同](../../integrations/bridge.md)，当前状态见[状态页](../../status.md)；下文原规划不作为另一份持续更新的契约。

## 1. 定位与已确认决定

企划集面向包含角色、世界观、参考素材与多图成果的创作企划。外部 Agent 或文本编辑器负责整理资料；Koma 挂载企划根目录，提供「角色／设定／参考／成果」面板；内置 ASK 从轻量导航按需读取原文、使用素材和提出草稿。

不新增常驻工作区，不在网页内制作复杂的档案编辑器，不用特定 XML 标签或文本段落正则猜测角色、服装、背景设定的语义结构。

| 已确认事项 | 本轮目标 |
| --- | --- |
| 目录与路径 | 从企划根目录识别 `characters/`、`lore/`、`references/` 及原有 `refs/`；对 UI、ASK 和外部状态统一输出根相对路径 |
| 角色参考图 | 同时支持角色目录内的 `refs/` 与 `extra/`，两者并存时合并展示，按完整路径去重 |
| 切换企划 | 读取新目录自身的任务文件，不自动把切换前活动任务板写入新目录；只有在当前目录下新建或显式关联保存才建立新映射 |
| 文件落盘 | 任务文件继续写 `slates/`，成果及回执、打标文本继续写 `assets/`，`save_ref` 继续写 `refs/`；不创建 `outputs/` |
| ASK 导航与容量 | `refs_index` 按角色聚合，一名角色一条摘要；提高索引容量；`read_ref` 每轮可读取 12 个文本文件 |
| 图片交接 | 内置 `chat_handoff`、`edit_handoff` 可使用企划图片路径和已读取的企划图片，确认后连同文字／参数准备到目标工作区 |
| 角色身份 | 企划 `char_id` 与画板 `c1/c2` 解耦，填入 TAG 是一次性应用，不建立文件与表单的隐式双向同步 |
| 协同控制文件 | `PROTOCOL.md`、`state.live.json`、`draft.inbox.json`、`live/` 保留原位置与责任 |

本轮不开放外部 Bridge 的 CHAT／EDIT 草稿，不增加自动生成、CHAT 自动发送、文件批量改写或新的付费流程。企划索引和面板无需 ASK 推理 Key；调用内置 ASK 仍需要文本连接。

## 3. 目录与元数据约定

### 3.1 标准结构

```text
<企划根目录>/
├── project.json                     # 可选：标题、简介、资料目录映射
├── characters/
│   └── <char_id>/
│       ├── char.json                 # 可选：姓名、别名、brief、TAG 与文件引用
│       ├── brief.md                  # 也支持 brief.txt
│       ├── profile.md                # 也支持 profile.txt
│       ├── tags.txt
│       ├── portrait.png              # 也支持 portrait.webp / portrait.jpg
│       ├── refs/                     # 角色专属参考图
│       └── extra/                    # 同样作为角色专属参考图目录
├── lore/                             # 自由组织的设定文档树
├── references/
│   ├── references.json               # 可选：标题、分类、用途说明
│   └── scene.png
├── refs/                             # 原有共享资料及 save_ref 保存内容
├── slates/*.slate.json                # 现有任务文件
├── assets/...                        # 现有成果图、图片名.json、图片名.txt
├── world-notes.md                    # 根层设定原稿也可浏览与读取
├── PROTOCOL.md                       # Koma 维护的协同说明
├── state.live.json                   # Koma 维护的状态
├── draft.inbox.json                  # 外部草稿投递槽
└── live/*.webp                       # Koma 维护的临时预览
```

所有资料项均可缺省；只存在 `brief` 与 TAG 的角色照常显示。无 `project.json` 时按约定扫描，企划标题回退为目录名；无 `char.json` 时姓名回退为角色子目录名。

角色目录下的 `refs/` 与根层 `refs/` 通过完整路径自然区分，例如 `characters/kuzuha/refs/weapon.png` 与 `refs/weapon.png`。读取按完整路径进行，不凭同名文件猜来源。

### 3.2 元数据格式与优先级

以下是首版实现拟采用的明确字段约定；Schema 校验仅针对结构、类型和路径，不分类或改写用户创作正文。

`project.json`：

```json
{
  "title": "示例企划",
  "description": "角色与世界观资料",
  "paths": {
    "characters": "characters",
    "lore": "lore",
    "references": "references"
  }
}
```

`paths` 仅配置资料目录，均相对于企划根目录；省略项使用标准名称。不用它重定向 `refs/` 保存、任务、成果或协同控制文件。不要求用户为默认目录重复填写映射。

`char.json`：

```json
{
  "name": "示例角色",
  "aliases": ["角色别名"],
  "brief": "负责夜间巡逻的守卫，性格谨慎，银发与红色披肩是外观记忆点。",
  "profile": "profile.md",
  "tags": {
    "prompt": "silver hair, red eyes",
    "negative": "",
    "outfits": [
      { "id": "main", "label": "主服装", "prompt": "uniform, red cape", "negative": "" },
      { "id": "casual", "label": "私服", "prompt": "white shirt, dark trousers", "negative": "" }
    ]
  },
  "portrait": "portrait.png",
  "refs": [
    { "file": "extra/weapon.png", "title": "武器设定", "description": "握柄和装饰细节" }
  ]
}
```

- `char_id` 取角色子目录名，身份同时包含所属企划；不使用本机画板的 `cN` 作为档案 ID。
- `brief` 可直接内嵌，也可通过 `brief_file` 指定文本。`tags` 可为一条原文字符串或上述分组对象，也可通过 `tags_file` 指定文本文件。
- 同一项按「有效的内嵌字段 → 显式文件引用 → 约定文件」选择来源。显式指向的文件缺失或格式错误时显示该项问题，不静默拿另一份内容冒充；未受影响的字段仍可使用。
- 约定文件按固定顺序选择：`brief.md`／`brief.txt`、`profile.md`／`profile.txt`、`portrait.png`／`.webp`／`.jpg`／`.jpeg`。有多份时来源路径可见，用户可用 JSON 显式指定。
- `char.json` 的文件路径相对于该角色目录；规范化后，面板和 ASK 一律看到企划根相对路径。角色文件引用留在所属角色目录中，不通过父级跳转取文件。
- 分组 TAG 将共同 `prompt/negative` 与用户所选的一套服装组合；没有选择时只用共同部分。普通 `tags.txt` 或字符串按原文处理，不自动拆服装、不清理权重、不猜正负词段落。
- 内嵌 TAG 的读取来源是实际 `char.json` 路径，并标明内容位于 `tags` 字段，不生成虚构的 `tags.txt` 路径。ASK 可通过 `read_ref` 读取该 JSON。
- JSON 未列出的 `refs/`／`extra/` 图片仍按文件名显示。条目说明不能改变文件真实身份或类型。

`references/references.json` 保留用户确认的结构：

```json
{
  "items": [
    { "file": "scene.png", "title": "夜间街景", "category": "场景", "description": "潮湿地面与暖色路灯参考" }
  ]
}
```

其中 `file` 相对于公共参考目录；未登记图片仍展示。原文按文本安全呈现，不执行 HTML、脚本或元数据中的命令。

### 3.3 设定、共享资料与成果识别

`lore/` 保留自由层级与文件原文；根层 TXT／Markdown 设定稿纳入设定列表，默认标题取文件名，不要求固定标题语法。`PROTOCOL.md` 和协同 JSON／`live/` 不归入设定。

根层 `refs/` 继续可读。一般文本作为共享资料可从设定栏访问，一般图片可从参考栏访问；有明确保存来源或已知配方／任务 Schema 的内容也进入成果栏。未知 Markdown 不靠正文关键词硬判为备忘录，可标为「共享文本」。同一文件在不同视图出现时共用一个路径身份与内容缓存。

成果识别详见第 9 节。浏览目录文件不自动导入任务、不自动恢复配方，也不改变图片所属工作区。

## 4. 扫描、刷新与资源生命周期

企划索引为当前挂载目录的派生视图，不复制整份企划到新数据库。复用现有单挂载、句柄恢复、目录锁、数据维护暂停与前台刷新机制。

扫描只进入约定／显式映射的资料目录，以及 `refs/`、`slates/`、`assets/` 和允许的根层设定文件，不递归遍历整个工程的其他目录。路径限制继续拒绝绝对路径、父级跳转、隐藏路径及已知凭据文件。

索引阶段允许读取有界的 `project.json`、`char.json`、`references.json` 和角色 brief；不预读完整 profile、独立 tags 正文，不批量解码原图。内嵌 tags 虽随 JSON 被本地解析，初始 ASK 状态仅列是否存在及读取来源。

工程容量起点拟设为：最多扫描 2048 个支持文件、16384 个目录条目、8 层子目录；初始角色摘要最多 128 条，设定／公共参考／共享资料分别采用独立分页，不能共享旧的 48 文件额度。brief 初始摘要最多 160 字，超出标明有完整来源；这些是实现预算，可在合成企划验收后调整，不是让模型遵守的创作限制。

完整已扫描目录与初始摘要分开。超过摘要容量的条目提供可继续读取的目录索引入口；建议复用 `read_ref` 的目录索引分页，不增加另一组工具。扫描达到总上限时明确 `limited` 与省略情况，不能将部分结果称作完整企划。

- 外部新增、修改、删除资料后，前台轮询、重新聚焦或显式刷新可更新目录；元数据按修改时间／大小缓存，显式刷新可重读。
- 单份 JSON 损坏、单张图片解码失败或一个引用缺失，只标记对应资料项；不因此中断整个企划浏览或外部草稿收件。
- 权限失效、目录断开属于挂载级错误，仍沿用恢复连接流程。
- 切换／卸载中止旧目录未完成的读取，迟到结果不能填入新企划。已冻结到 ASK 消息／草稿中的素材继续由原资源持有者管理。
- 缩略图按可见范围／详情打开按需生成，原图与 URL 不进深层 reactive；关闭、切换与销毁释放不再被引用的资源。
- 浏览器不支持目录 API 时保留现有 JSON 导入／下载入口，明确无法挂载企划目录，不声称手动 JSON 已提供完整企划集能力。

## 5. Slate 与目录绑定：消除跨企划串写

### 5.1 目标行为

| 事件 | 目录与任务行为 |
| --- | --- |
| 首次挂载或从 A 切到 B | 读取 B 的企划资料、已保存映射与 `slates/*.slate.json`；不根据当前活动 Slate 创建新映射 |
| B 中有未导入或已修改任务文件 | 成果栏可显示文件；写入本机任务仍走已有草稿审阅与版本检查 |
| B 中有已关联任务 | 恢复 B 自身映射并继续原同步；不以其他目录的交付回执判为已同步 |
| B 挂载期间新建任务 | 创建操作明确属于 B 时，按原流程关联并写入 B |
| 手动选择一个旧任务作为活动任务 | 仅切换活动任务，不自动关联 B |
| 用户选择「关联／保存到当前企划」 | 显式建立映射并同步，保留已有文件冲突处理 |
| 用户确认要求目录交付的草稿 | `directory_required` 仍代表这次明确交付意图；使用草稿冻结的目录，不能在确认前切换后投递到另一企划 |
| 卸载、切板或删除 ASK 会话 | 不删除本机任务、目录文件或已交付成果 |

挂载读取现有任务不等于自动采用外部修改。既有本机内容、外部文件与版本冲突继续经审阅处理；挂载本身不抢换用户正在工作的本机任务。

### 5.2 必须一起处理的异步边界

不能只删掉 `attach()` 中的活动任务映射：创建／交付回调目前也会取调用时的活动目录。新建、显式关联与带目录意图的草稿都须捕获来源目录身份，避免操作在 A 开始、异步完成时已经切到 B。

同一要求覆盖手动创建、ASK 新建、外部任务文件导入、失败重试及撤销／恢复：不得借由 `created` 或 `required` 标记自动改挂到新目录。没有目录意图的操作仍可作为纯本地任务完成；有明确目录目标而目标断开时保留待处理状态，不另选目录。

已有同目录映射继续使用，不搬移既有文件。若某任务由用户明确关联过多个目录，各映射与交付状态分别保留，不能凭活动状态为其他目录补建关联。

控制文件位置和状态导出用途不变；它们仍描述当前工作台。`active_slate` 是活动任务摘要，不是“该任务属于此企划且已经落盘”的证明，外部协同说明需明确这一点。

## 6. ASK 分层索引与读取配额

### 6.1 `refs_index` 的目标结构

初始状态提供企划身份、简短介绍与分层导航。一名角色只占一条记录，关联文件作为该记录内的路径，不重复摊入普通文件列表。

```json
{
  "available": true,
  "project": { "title": "示例企划", "description": "角色与世界观资料" },
  "characters": [
    {
      "id": "kuzuha",
      "name": "示例角色",
      "aliases": ["角色别名"],
      "brief": "谨慎的巡逻守卫，银发与红色披肩。",
      "brief_path": "characters/kuzuha/char.json",
      "tags": { "available": true, "path": "characters/kuzuha/char.json", "field": "tags" },
      "profile": "characters/kuzuha/profile.md",
      "portrait": "characters/kuzuha/portrait.png",
      "refs": [{ "path": "characters/kuzuha/extra/weapon.png", "title": "武器设定" }]
    }
  ],
  "lore": [{ "path": "lore/world.md", "title": "world", "bytes": 1200 }],
  "references": [{ "path": "references/scene.png", "title": "夜间街景", "category": "场景", "description": "暖色路灯参考" }],
  "files": [{ "path": "refs/style.md", "bytes": 800 }],
  "limited": false
}
```

上例省略各分组计数与分页字段。实现须为分组提供 `total`、`omitted` 与继续读取入口；角色参考图较多时也保留数量和所属目录入口，不能为一名角色把全部图片路径无限展开。缺失项明确为空／不可用，不生成假路径。

`read_ref` 保持一个入口：文件路径读取原文／图片，目录路径读取有界的结构化索引页。目录索引的 `offset` 是条目偏移，文本的 `offset` 是字符偏移，返回类型与 `next_offset` 明确区分。索引页不占文本文件名额，但仍属于工具结果与上下文预算。

UI、初始 `<workspace_state>`、`get_state` 与外部 `state.live.json` 共用同一份企划索引。句柄、本机绝对路径和控制器不进入模型状态。新路径规则是根相对路径，旧消息中已冻结的内容保持原样，不按新规则重读旧消息或搬动文件。

### 6.2 12 个文本文件的计数口径

此次放宽针对 `read_ref` 工具读取，不顺便扩大手动附件入口：

- 每轮最多读取 **12 个不同文本文件**；同文件分页、重复读取及对其不同内容的引用不重复计数。
- 手动文本附件仍按现有 4 个限制；工具文本与手动文本分开计数。两者仍共用配置中的总字符预算与本页内存上限，不把「12 个文件」解释为无限正文。
- 单文件字符限制、总字符限制、每次 8000 字文本分页及本页 200 MiB 资源上限保持现有规则。
- 图片名额和视觉调用预算保持现有规则，不随文本数一起翻倍。
- 首次成功读取固定本轮文件版本；下一轮可读新版本。失败读取不消耗成功文件名额，不留下无主附件。
- 重试、编辑重答、压缩召回和收藏恢复保留工具读取来源，不能把工具文本改当手动附件而重新卡在 4 个限制，或绕过总字符预算。

计数调整应落在附件容量检查与读取来源的统一规则上，不能只修改 `read_ref` 描述或临时跳过校验。

## 7. 企划图片的 ASK 草稿交接

### 7.1 两种输入都应可用

内置交接草稿保持现有字段，在图片引用位置支持：

| 输入 | 示例 | 解析规则 |
| --- | --- | --- |
| 现有工作区图片编号 | `#h7`、`#f3`、`#c1.2`、`#e2.1` | 保留现有冻结引用与可用性检查 |
| 企划根相对路径 | `characters/kuzuha/portrait.png`、`references/scene.png` | 必须属于本轮企划目录快照；提议草稿时读取并冻结实际图片 |
| 已读取的企划图片编号 | `read_ref` 返回的 `#aN` | 接受程序确认具有企划来源的图片，复用已冻结原图 |

例如 `chat_handoff.images` 可为 `["characters/kuzuha/portrait.png"]`，`edit_handoff.image` 可为 `"references/scene.png"`；仍沿用同一步骤里的文字、选项与编辑参数。路径长度按资料路径规则处理，不能继续套用短图片编号的长度限制。

本轮只放开有企划来源的附件，不将所有无来源的 `#a` 一并开放为交接图片。来源由本机读取／面板附加时登记，不能由模型伪造路径字段取得资格。企划面板附加的图片也须保留来源，不能调用通用附件方法后丢掉身份。

### 7.2 冻结、应用与撤销

在现有草稿解析前增加异步素材准备，由只读资料端口完成路径解析、图片校验与字节冻结；现有纯草稿校验继续处理已经解析好的引用，不直接操作目录句柄。

冻结记录关联企划目录身份、完整相对路径、内容哈希、尺寸与实际原图。图片字节交给现有附件／资源池持有，草稿保存稳定引用；不把 Blob 塞入深层响应式状态或模型输出的 JSON。

- 直接路径未读取成功时不创建可应用草稿。读取期间切换目录，中止旧读取，不到新目录查找同名文件。
- 路径与已读取 `#aN` 指向同一冻结版本时复用资源，不重复拷贝或占图像名额。
- 草稿确认使用预览对应的冻结字节。之后外部改图、删图或卸载目录，不把已有草稿悄悄替换成另一版本；需要最新版时重新读取并提议。
- 冻结素材仍有效时可按现有确认流程应用，不额外要求重新挂载目录；若素材已释放或未随收藏保存，显示来源失效，不凭同名路径回填。
- 待确认草稿、收藏会话、页面撤销／恢复共同引用素材；相应记录释放后回收。收藏恢复必须能找到实际保存的图片，不能只保存磁盘路径。
- CHAT 确认后新建／复用空白会话并准备参考图、选项和输入文字；EDIT 确认后准备编辑画板。继续遵循已有目标冲突、尺寸、模型能力和撤销规则，不触发生成或发送。
- 使用原图而非卡片缩略图或 ASK 的视觉压缩图；需要适配目标工作区大小时沿用已有导入处理，并保留来源信息。
- 无真实生成参数的立绘只作为素材，不用当前画板参数伪造该文件的生成回执。当前表单或模型默认值可以作为新编辑配置，但不冒充源图参数。

准备交接素材不等于模型已经看过图片。视觉分析继续使用 `read_ref`／视觉工具及原预算；仅元数据轮次不把图片像素发送给模型。直接指定材料可在本地为草稿准备，不因此声称看过画面。

此扩展仅进入内置 ASK Schema 与校验／写入通路；外部 Bridge 仍只接收既有 IMAGE 草稿。不能因内外复用 Schema 而意外开放外部 CHAT／EDIT 写入。

## 8. 企划集界面与工作区联动

### 8.1 入口与四栏

沿用 HOME 与 ASK 输入框旁的目录入口。未挂载显示「企划目录」，已挂载显示企划标题，点击打开企划集面板。切换、刷新、卸载放在面板管理菜单；设置中的原管理与手动 JSON 入口保留。

| 栏目 | 主要内容 | 操作 |
| --- | --- | --- |
| 角色 | 立绘、姓名／别名、brief、TAG 可用状态；详情分层呈现 TAG、参考与完整人设 | 引用给 ASK、复制 TAG、填入角色栏、将立绘送入 CHAT／EDIT 或 IMAGE 参考 |
| 设定 | `lore/`、根层设定稿及共享文本的目录树／列表 | 打开原文、引用给 ASK；原文很长时分段加载但可继续读完 |
| 参考 | 公共图与根层共享图片，标题、分类、说明 | 大图检视、ASK 附件、IMAGE 参考、CHAT／EDIT 导入 |
| 成果 | 当前企划的任务文件、原图、回执、打标文本和保存资料 | 查看／下载、打开已有任务或审阅外部任务；不以浏览代替应用 |

复用现有弹层、页签、菜单、图片预览与按钮，按照当前设计语言组织密度与层次。按内容需要使用网格、列表、详情视图，不把全部字段强制改成一行一个值；不另造全局样式补丁、常驻工作区或复杂档案编辑表单。具体视觉方案在实现前以现有组件预览核对，本规划不虚构已经验收的样式。

### 8.2 角色与图片的一次性使用

「填入角色栏」允许选择已有槽或新增槽；新增由 Drawing 分配 `cN`，替换只修改用户选定的槽位。选择服装后使用共同 TAG 加该套服装，不能把所有服装串在一起。角色数量与模型能力沿用原规则，无可用槽时给出明确反馈。

企划角色标识不成为画板槽位 ID，也不建立外部文件变化后覆盖当前 Prompt 的自动监听。用户调整画板后，不回写 `char.json` 或 `tags.txt`。

「引用给 ASK」只预填角色／文件引用并打开现有 ASK，不自动提交问题或把完整档案作为附件塞入上下文。「作为 ASK 附件」是明确附加实际文件的另一种操作，并保留企划来源。

CHAT、EDIT 与 IMAGE 参考入口分别调用原有导入／交接／参考资产服务。IMAGE 必须按当前支持的参考类型处理，浏览不启用参考、不进行付费编码；不可用时说明原因。导入准备不自动触发生成或发送，原有必要的能力／引用限制继续生效。

## 9. 成果聚合与现有写入路径

| 来源 | 呈现方式 | 仍由谁写入 |
| --- | --- | --- |
| `slates/*.slate.json` | 任务标题、状态、交付项与文件状态；未采用的外部文件标明待审阅 | 现有 Slate 同步与草稿确认 |
| `assets/...` | 原图与配套 `图片名.json`／`图片名.txt` 组成一份成果，避免三条重复卡片 | 现有绑定成果交付 |
| `refs/` 配方／任务 JSON | 按已知 Schema 展示保存资料，读取时检查真实内容 | 现有 `save_ref` |
| `refs/` 备忘录与共享文本／图片 | 有保存来源时显示相应类型；未知文件用中性类型与文件名 | 外部编辑器或现有 `save_ref` |

成果视图仅聚合当前目录中的真实文件与该目录映射，不从全部本机 Slate／历史／收藏中拼出假成果。映射有记录但文件缺失时标为缺失；文件存在但无本机映射时可浏览原件，不伪造已导入或已交付状态。

`slates/` 中的活动任务文件与 `refs/` 中保存的任务快照语义不同，不能把后者自动当作双向同步文件。未知成果图片可显示，但不得补造回执或把文件存在等同于任务完成。

不迁移、重命名、复制既有目录内容，不创建 `outputs/`，不修改现有 `assets/` 路径校验。文件写入仍保留目录目标冻结、冲突检查、失败补偿、用户确认及撤销的所有权判断。

## 11. 验收案例

| 场景 | 必须验证的结果 |
| --- | --- |
| 仅约定文件，无任何 JSON | 角色名称回退、brief／profile／tags／portrait 路径正确，仍可使用 |

| 在 A 新建／关联时切换到 B | 异步结束不写 B；带目录意图的草稿目标不漂移 |
| B 已有任务与外部修改 | 可列出，采用须经原草稿审阅；版本与成果所有权检查不被跳过 |

| 企划图片交接 | 直接路径、`read_ref` 图片、面板附加图片均能带文字交接 CHAT／EDIT；普通无企划来源附件不被误放行 |
| 文件同名换图／卸载 | 已提议草稿使用冻结原图；未完成读取取消；重新提议才取得新版本 |
| 图片生命周期 | 应用、取消、失败、撤销／恢复、收藏待确认草稿及刷新恢复无丢图、错误释放或串会话 |
| 成果聚合 | 图＋回执＋打标配成一项；只显示当前目录内容；保存任务快照不成为活动同步任务 |
| 字段和路径兼容 | `refs/` 原文件无需搬动；所有新索引路径根相对；控制文件不进入设定／参考卡片 |
| 功能边界 | 面板操作与 ASK 草稿不生成／发送；外部 Bridge 仍拒绝 CHAT／EDIT 写入；无目录 API 时反馈准确 |

逻辑与 Schema 用合成目录、文本和图片验证；浏览器测试验证真实业务动作、请求、状态、文件内容及生命周期，不断言字号、圆角、间距或视口几何。按改动运行 `npm run check` 和目录／ASK 交接／Slate 的必要浏览器用例，界面另行目视核对。真实本机目录授权与刷新恢复单独记录，不以模拟结果代替。
