## 2. 官方能力与用词

这里的“多角色分区”指将基础描述与各角色描述分开，让不同角色的外貌、服饰、动作较少相互串染。图像抠图、蒙版分割、角色参考图和 Vibe Transfer 是另外的能力，不纳入本专题。

| 能力 | V4.5 Full／Curated | V5 Full／Curated |
| --- | --- | --- |
| 独立角色描述 | 最多 6 个 | 最多 22 个 |
| 每角色独立 Negative | 支持 | 支持 |
| 自动安排角色位置 | 支持 | 支持 |
| 自定义位置 | 5×5 网格 | 自由放置，定位方式已重做 |

官方多角色文档把 V4 系列上限列为 6；V4.5 模型页明确链接该能力。V5 两个型号的模型页均明确列出 22 个角色。上述数字是官方产品能力，不能直接当作所有兼容网关的已验证上限，也不保证复杂多人构图的成图质量。

Koma 的单幅插画分工采用用户确认的实践规则：

- 基础 Prompt：画师画风、总人数、镜头、场景、动作与表情。人数标签如 `2girls` 放在基础描述。
- 角色 Prompt：以 `girl`／`boy`／`other` 等不带人数的主体词开头，仅承载该角色的外貌、衣着或具名版权角色名及可选施受方向前缀；常规动作留在基础描述，仅整页多格漫画手册例外。
- 角色 Negative：约束该角色不应出现的内容，可用于减少角色间特征串染。
- 角色顺序：参与构图；官方说明通常按从上到下、从左到右安排，手动位置宜与顺序及文字描述一致。

官方还提供 `source#`、`target#`、`mutual#` 动作标签，用于描述互动的主动、被动或相互关系；其效果不保证稳定，本期不增加专用动作编辑器。

官方界面支持 `基础描述 | 角色 1 | 角色 2` 简写，并明确它不能与角色输入框同时使用。当前 Koma 未实现竖线拆分，也未核验上游会如何解析；不能把现有混写文本视为已建立独立角色。竖线的导入、转换与共存规则留待设计讨论，不自动重写用户现有提示词。

## 3. 协议事实

### 3.1 NovelAI 官方

官方图像 Schema 的字段关系如下，属于生成请求的 `parameters`，不是新的顶层 API：

```text
parameters
├─ v4_prompt
│  ├─ caption
│  │  ├─ base_caption: string
│  │  └─ char_captions: [{ char_caption: string, centers: [{ x: number, y: number }] }]
│  ├─ use_coords: boolean
│  └─ use_order: boolean
└─ v4_negative_prompt
   └─ 同属 V4ConditionInput，具有相同字段结构
```

字段名称仍以 `v4_` 开头，不能因使用 V5 就自行改为 `v5_`。正负角色列表应按同一角色顺序构建，空的角色 Negative 也应保留对应关系，不能过滤空项导致错位；具体发送约束须在协议联调中确认。

Schema 将 `centers` 定义为数组，将 `x`／`y` 定义为数字；本轮资料没有给出完整的范围校验和多中心使用规则。后续需核验坐标范围、V4.5 网格转换和 V5 连续坐标约定。领域数据应保留原始坐标精度，显示网格标签不能成为唯一存储格式。

### 3.2 标准网关（初次勘探记录）

公开客户端已观察到以下路径：

- 工具请求把 `sourceParams.characters` 赋给 `payload.characters`。
- 统一图片客户端保留业务字段，分别发给生成或工具的报价、执行接口，并在执行时带上当次 `max_cost`。

这些证据尚未给出 `characters` 内每一项的正式 Schema。不能直接假设网关角色字段等于官方 `char_captions`，也不能根据工具路径推定基础生成与原生入口的行为一致。

实现前需核对：标准网关的角色项字段、正负词与坐标表达、数量限制，以及报价／Studio／原生／工具各路线如何保留同一份角色信息。按协议能力适配，不新增私有渠道 Profile，不按域名猜测支持情况，不自动回退路线。

### 3.3 用户登录后的接口文档复核（2026-10-23）

已读取页面的 Studio 生图字段表、NovelAI 媒体请求示例、模型目录说明，以及页面“Download reference JSON”导出的 v3 参考（69 个操作）。结果如下：

| 位置 | 文档明确提供 | 对多角色接线的意义 |
| --- | --- | --- |
| `POST /v1/image/estimate`、`POST /v1/image/generate` | 相同的基础 model／prompt／negative_prompt／尺寸／采样／Seed／改写开关字段；报价采用同一生成设置 | 字段表及示例均未列出 `characters`，不能据此确定角色项结构 |
| `POST /v1/image/tools/estimate`、`POST /v1/image/tools/run` | 工具、源图、蒙版及基础提示词示例 | 没有独立角色项示例或正负词／坐标映射说明 |
| 媒体 → NovelAI → `/ai/generate-image` | 原生请求包含 `parameters.v4_prompt` 与 `v4_negative_prompt`，各自有 `caption.base_caption`、空 `char_captions`、`use_coords: false`、`use_order: true` | 确认页面展示官方式原生外层结构；空数组没有证明非空角色项怎样映射至 Studio `characters` |
| NovelAI 详细说明 | 明确提示该适配器已安装，但当前部署未包含详细映射指南 | 不能把安装状态当作角色功能和各路线一致性的实测结果 |

导出的接口参考 JSON 中没有 `characters`、`char_captions`、`use_coords` 或 `centers` 字段；原生示例是媒体页面单独加载的内容，并不在该导出内。页面另提供通用 request／response Schema 下载链接；request 链接本次被浏览器客户端阻止，未读取其内容，因此不对这份独立 Schema 是否含相关定义下结论。

本次补齐了原生请求外层结构的证据，仍缺**非空 Studio `characters` 的实际字段示例**，以及报价、Studio、原生和工具路线的映射关系。缺少文档不等于上游不支持；当前标准网关的接入限制维持。复核只读文档，未调用报价、生成或工具执行接口。

### 3.4 实际接口探测：角色结构已观察（2026-10-23）

用户随后要求测试真实接口，并在本机临时文件提供 Key。共进行了 10 次已鉴权报价与 3 次只读元数据解析，全部返回 HTTP 200；此前无 Key 的一次报价返回 401。没有调用生成、编辑执行、放大或推理接口。临时 Key 在探测结束后删除，结果只记录合成参数、校验响应和报价，不记录凭据或账户余额。

**真实服务端返回的标准角色结构：** 向 `/v1/image/inspect` 上传带有官方 NAI 正负角色元数据的 64×64 合成 PNG，响应的 `parameters` 包含：

```json
{
  "use_coords": true,
  "characters": [
    {
      "prompt": "girl, red hair, white dress",
      "uc": "blue hair",
      "center": { "x": 0.3, "y": 0.5 }
    },
    {
      "prompt": "boy, blue hair, black coat",
      "uc": "",
      "center": { "x": 0.7, "y": 0.5 }
    }
  ]
}
```

| 本地领域字段 | 实际观察到的标准网关字段 | 观察范围 |
| --- | --- | --- |
| `characters[].prompt` | `characters[].prompt` | 正向词原文保留 |
| `characters[].negative` | `characters[].uc` | 第二角色为空时仍保留对应项，无错位 |
| `characters[].centers` | `characters[].center` 单个对象 | 已观察单中心；多中心尚未测试，不可静默丢弃 |
| `placement` | 顶层 `use_coords` | manual 返回 true；auto 返回 false，中心数值仍保留 |
| `id`／`on`／画板归属 | 不属于该标准角色项 | 上游返回的角色项没有这些本地字段，出站时应只发送启用角色 |

V4.5 手动与自动各一个样例；V5 手动样例的 0.24／0.76 连续坐标在解析结果中原样保留。这证明解析行为，不证明生成模型的实际定位效果或数量上限。

将上述**服务端返回的角色项**和 use_coords 原样提交到 `/v1/studio/image/estimate`、文档中的 `/v1/image/estimate`，V4.5 手动／自动与 V5 手动均返回有效报价。与此同时，`characters` 为字符串、角色项为字符串、两种未确认候选结构也都得到 HTTP 200，因此报价没有提供足以区分角色格式的校验信号。宽度无效值对照返回了不同的付费报价，未执行该报价。

结论：此前“没有非空角色项示例”的缺口已由实际解析响应补齐，接线采用 `prompt / uc / center` 加顶层 `use_coords`；不能把本地 `negative / centers / placement` 直接透传。**生成端是否读取并采用这些字段仍未实测**。探测阶段未改代码，随后 C2 已完成接线并移除临时拦截，见 §3.5。源响应与探测脚本位于本机忽略目录 `.local/research/novelai-multi-character/probe/`。

### 3.5 C2 映射落地（2026-10-23）

- 标准报价、重报、Studio 与工具请求统一映射为 `characters: [{ prompt, uc, center }]` 与顶层 `use_coords`。仅发送启用角色，不发送本地 ID、启停或画板归属；零角色维持既有请求。
- 免费原生与官方 NAI 从同一份领域快照构造 `v4_prompt`／`v4_negative_prompt`，避免预报价先转成标准字段后丢失 Negative 或坐标。空 Negative 保留对应项，执行不受后续表单编辑影响。
- 官方与标准元数据均可还原为本地结构，接入导入／复用／历史／收藏／编辑交接。V4.5 提交投影格中心，V5 保留连续坐标；原始本地位置不受提交投影覆盖。
- 标准格式仅观察到单中心。手动模式含多个中心时提示在现有定位板重选单点；自动模式关闭定位，仍可提交。导入原文及官方多中心数组保留，不伪造未确认字段。

本轮 `npm run check`（192 项单元检查）与 25 项相关浏览器用例通过，含生产构建的本地代理转发；详见[收口记录](multi-character-boards-plan.md#c2-标准网关补齐与收口)。这些用例验证本地请求与数据往返，真实生成效果和费用仍待实测。

## 5. 后续实现应保持的语义

以下是接入要求，具体类型与交互已细化在[基础实施计划](multi-character-boards-plan.md)：

1. **基础描述与角色独立保存。** 不通过程序猜测全文语义，将原提示词自动切成角色。零角色时保持现有单一 Prompt／Negative 的行为。
2. **角色有稳定身份与明确顺序。** 延续 ASK 预留的 `characters: [{ id, prompt, negative, position }]` 方向；内部位置结构需容纳官方坐标。新增、删除和重排不能把旧草稿的下标悄悄指向另一个角色。
3. **未设置位置与手动位置可区分。** 自动安排不等于把所有角色写为中心点。切换到 V4.5 时不能静默覆盖 V5 原始坐标或删除超出上限的角色；网格投影、保留原值与超额处理见实施计划 §4.1。
4. **一次提交使用同一份快照。** 报价、重新报价、执行和历史记录携带一致的角色内容；执行期间编辑表单不改变在途请求。沿用 N=1、费用上限、失败停止与取消行为。
5. **ASK 按对象决定是否预载。** 活动画板的基础词文和角色原文完整随初始状态提供；其他画板仅给目录，无图片锚点时不预载历史图词文，按需通过工具读取。
6. **ASK 写入仍经过草稿。** 角色内容与顺序已纳入源画板快照、冲突判断与撤销记录，hash 覆盖源画板和完整生成表单。新增、删除、重排、启停和定位的 character_edit 已接入，详见实施计划 §6、§9。
7. **保存遵循原数据边界。** 普通历史与 ASK 对话仍只在本页内存；绘图草稿、收藏与新版 Koma 备份按既有写入和租约机制扩展。旧 Koma 数据缺少角色字段时按零角色读取，不新增旧应用迁移流程。

本期不扩展 Vibe、参考图、官方重绘／放大、CHAT 的角色生成协议或新的生图工具。提示词仅在功能落地后，在用户当前版本上补充接口事实与已确认的角色分工，保留创作正文。

## 6. 实施顺序

早期建议已细化为[基础实施计划 §8](multi-character-boards-plan.md#8-实施阶段与验收)：C1 数据与角色 UI → C2 请求与参数往返 → C3 画板 UI 与保存 → C4 ASK 读取与草稿 → C5 提示词与收口。数据结构一次覆盖画板与角色，实施先跑通角色；标准网关在取得 §3.4 字段证据后完成接线。

C1–C5 基础实现已完成本地收口，包含 C2 官方与标准网关请求映射及参数往返。真实收费生成按工程约定独立授权，模拟测试用于验证请求构建与前端行为。

## 7. 已确定的 UI 与基础边界

- 角色采用方案 A：基础描述下的独立折叠角色区，包含 Prompt／Negative、启停、增删、排序和定位。
- 画板采用方案 A：表单顶部整行分段胶囊下拉，右侧加号复制当前；菜单支持新建空白，补齐改名与删除。胶囊层次以已调整本地原型为准。
- V4.5 用 5×5 网格，V5 用自由坐标；模型切换不删除超额角色，不覆盖未编辑的原始坐标。
- 前端不猜语义或自动拆分竖线；ASK 使用基础改写与角色动作草稿，经用户确认后应用。
- 活动画板的基础词文与角色原文随初始状态提供，其他画板仅给目录，无图片锚点时不预载历史图词文；靶点使用画板 ID 与稳定角色 ID，检查点／撤销覆盖角色组与画板归属。

原型来源、具体交互、四视口要求与未搬入的演示行为见[实施计划 §2](multi-character-boards-plan.md#2-前端迁入基线)，正式页面与模拟验收结果见该文 §9。

## 8. 验收重点与来源

实施阶段需要验证：

- 零角色生成行为保持；多人正向词、Negative 和顺序能在各条已开放路线一致发送，空 Negative 不导致串位。
- 自动／手动定位、V4.5／V5 切换不静默丢失数据；元数据读取与复用不把 V5 坐标永久量化为网格标签。
- 批量、报价更新、取消、失败与在途编辑不改变已捕获的角色快照。
- 参数保存与往返不丢角色；ASK 角色草稿在删除、重排、外部修改后不会误写，撤销／恢复保持完整。
- UI 按批准方案检查四视口；模拟契约验收和供应商实测分开记录。
