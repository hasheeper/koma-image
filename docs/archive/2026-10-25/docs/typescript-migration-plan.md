## 3. 勘探发现与处理原则

### 声明不能代替实现检查

T0 时 `media.js` 的 `NAI_UPSCALE_MAX_PIXELS`、`EDITOR_MODES`、`buildUpscalePayload` 和 `buildNAIEditPayload` 四个实际导出未出现在 `media.d.ts` 中；当时 TS 调用方没有直接使用这些导出，不能据此判定现有功能故障。T2 已保留这些导出并直接在实现中定义类型。

T0 时 `MaskState.strokes` 是 `unknown[]`，无法表达普通笔画与清空记录的差别；`ImageMetadata.fields` 是宽泛的字典，未区分可导入的数字与文本字段。T3／T4 已分别改为明确的可选字段与笔画联合类型。media 原先统一声明返回带任意键的 `ImagePayload`；T2 已改为具体请求联合类型，并保持与网关边界兼容。

### 同一数据结构只保留一个权威定义

| 边界 | 实施方式 |
| --- | --- |
| 会话／轮次／版本／消息 | 复用 `storage/records.ts` 的 `ConversationRecord`、`ConversationTurn`、`ConversationVersion`、`MessageBlock`；不另建一套近似模型 |
| 模型目录 | 复用 `domain/catalog.ts` 的 `CatalogModel`；仅需要 models／samplers 的函数采用实际使用的最小结构 |
| 媒体参数 | 将已有 `EditorMode`、`EditMode`、`EditorFields` 移入 TS 实现；为不同输出补足具体结构，并保持可传给现有 `ImagePayload` 网关边界 |
| 图片元数据 | 本模块定义明确的可选字段与 extras；原始 JSON 先作为 `unknown`，在访问处收窄，不把解析结果直接断言成完整内部模型 |
| 蒙版 | 本模块定义 `MaskPoint`、普通笔画、清空记录及 `MaskState`；采用可区分的联合类型，保持 snapshot 的现有运行时结构 |
| 波浪 | 本模块区分公开控制接口和带 canvas／visible 的内部实例；标明 `boolean \| null`、完成回调、图像源与 TypedArray 状态 |

类型优先放在所属模块并通过 `import type` 引用；确有多个实现共享时才抽取小型类型文件。不新增全局 `types/` 大杂烩、泛型驱动框架或运行时 schema 依赖。

### 收窄类型不能顺便改变业务

- 保留 0、空字符串、`null`、`undefined` 的原有区别。例如图片元数据的 `finiteNumber` 使用 `Number(value)`，与 `domain/value.ts` 的 `finite` 对空值的处理不同，不能为了共用工具直接替换。
- 保留会话原地修改、复制时的 ID 重映射、附件消费、迟到结果的 selectionRevision 判断与原报错时机。布尔值相减排序可改为显式 `Number(...)`，但置顶和稳定排序规则不变。
- 请求字段白名单、图片次序、源图与 EXIF 归一化 PNG 的选择、Seed 0、8MB／32MB 上限、模型面积和蒙版尺寸判断保持一致。
- 解析边界需明确哪些输入已有检查、哪些是内部不变量。新增对异常文件的拒绝、容错或默认值均属于行为变化；发现问题单独记录和验证，不伪装成类型补丁混入迁移。
- Canvas context 的可空性、Promise 的完成值、`ImageBitmap` 与 `HTMLImageElement` 的不同清理方法必须表达清楚。优先保留现有检查；新增失败分支须说明影响，不能用批量 `!`、`as any` 或 `as unknown as` 掩盖问题。
- 已存在的宽泛 JSON 持久化结构不在本轮全面收紧。`storage/records.ts` 与 conversation 都有 `assetRefs`；这次不顺便合并或改变依赖方向。

### 原生驱动继续保持原生

TS 类型会在构建时擦除；高频驱动改成 `.ts` 并不要求接入 Vue reactive。保持独立 Canvas 宿主、普通局部变量、Map／Set、同一 rAF 调度与 Observer 管理，维持暂停／恢复／销毁责任。指针逐点数据、Blob、ImageBitmap 和完整蒙版不移入深层响应式状态。

### 隔离试验结果

在忽略提交的 `.local/ts-migration/discovery/` 复制应用源码，仅将 9 个 JS 改名、移除配对声明并替换相关导入，使用继承当前配置的 `vue-tsc` 检查，得到 **351 条诊断**。其中包括 188 条未标注参数，以及未迁入的导出类型引起的下游连锁报错。这只是证明“仅改后缀不能完成迁移”，**不代表 351 个运行 Bug，也不作为工作量估算**。

T0 时正式源码的 `npm run typecheck` 与 52 项单元测试通过；当时未重跑浏览器与完整发布验收。试验副本不是迁移成果，不复制回正式目录。后续 T1／T2 的验证另见第 8 节。

### T1：用两个基础模块确定迁移方式

先迁 `image-dimensions`，为后续 media 提供真实的类型来源；再迁 `prompt-converter`。

- 补齐尺寸返回值、字节索引辅助函数、文本片段、分隔符与权重解析结果的类型。
- 保持 PNG／JPEG／WebP 解析算法、转义／嵌套／权重计算与显式点击转换的触发方式。
- 改名、补类型、删除对应 `.d.ts`、替换调用方导入放在同一个可检查的改动中。
- 只为当前测试缺失且与本次收窄有关的格式分支补小型合成样例；优先关注 JPEG／WebP 尺寸与嵌套权重，不建立新的图片测试平台。

### T2：业务模块优先形成可靠的类型边界

先完成 conversation，再完成 media；可以形成两个独立提交。

- conversation 显式声明创建结果、版本状态、消息联合类型、Map／Set 及可空父节点；清晰处理 `filter`／`find` 结果，不用断言掩盖 ID 缺失。
- media 核对全部真实导出。参数校验约束合法字段名，显式列出校验后的数值字段；区分聊天生成／带图编辑、图生图、重绘与放大的输出。
- 默认参数、条件字段的有无、图片原字节／PNG 路径、独立放大描述，以及内部 validation 的执行费用检查分支全部保留。
- `services/chat.ts`／`editor.ts` 只做必要适配。持久化记录、数据库版本和备份 v2 不变；无新增数据转换。
- 此阶段可在 TS 控制流确有需要时做等价局部重写；避免提取大框架、不可变状态重构或将服务改成 Vue store。

### T3：外部数据与图片资源

建议逐个处理 `image-meta → native-images → comparison`，不把三个解析／合成流程合并。

- 元数据区分原始 JSON、已读取的文本块和可导入字段；保留压缩文本、中文解码、采样器映射、只读 extras 及 CFG Rescale 不导入 CFG 的规则。
- 二进制模块标明 `ArrayBuffer`、TypedArray、解压流、分块数组与 Blob；核实 TS 6 的缓冲区泛型，避免为消除报错无故复制整张图片。
- ZIP 条目数、CRC、单张与总解压大小限制以及错误信息保持原样。Node 用例仍可直接导入纯解析模块。
- 对比图明确 `Promise<Blob>`、尺寸结果、Canvas 上下文、图像资源和释放函数；维持布局、字体、取消检查点与 `finally` 清理。测试覆盖解码 fallback 时是否需要补充，按实际代码改动决定。

### T4：最后迁移高频 Canvas 驱动

先 mask-editor，再 tile-wave。每个驱动独立检查后再继续下一个。

- 蒙版的活动笔画可空，完成笔画与清空记录可区分；编码缓存保留 `undefined`（待计算）、`null`（空蒙版）、字符串（已有蒙版）三种状态。
- 保留 pointer capture、双指取消、undo／redo、源像素坐标、32 阈值及 snapshot／restore 结构。事件列表使用准确的事件名和处理函数类型。
- 波浪明确共享 Set／WeakMap、尚未观察到的 visible 状态、揭示计时器和完成回调；保留 reduced-motion、后台／离屏跳过与 reset／destroy 的 Promise 完成语义。
- `tile-wave` 在模块加载时依赖 `matchMedia` 和 Observer，继续由真实浏览器套件验证；不为纯 Node 导入而重写调度或伪造全套 DOM。
- `WaveHost.vue`、`ChatPrint.vue`、`EditorOverlay.vue` 和 `editor-canvas.ts` 接入新类型，模板、CSS、动效参数及响应式所有权不改。

### T5：收口而非扩大范围

- 核对 9 个模块原来的每个导出及所有直接／间接调用方，确认没有指向已删除 `.js` 的运行时导入。
- 删除这 9 份过渡声明；保留 `env.d.ts` 等真正的环境声明。实现内导出的类型成为唯一来源。
- 不保留旧 JS 转发壳、双份实现或构建后源码副本。每个阶段均可正常构建，最终 `src/` 的自有逻辑由 TS／Vue TS 承载。
- 更新本文状态和受影响的实现文档，记录真实执行的检查、剩余限制与最终文件统计。
- Git 提交按阶段组织；推送 GitHub 和部署 Pages 是单独交付动作，按工程约定与当次用户授权执行。

## 5. 工具、导入和迁移纪律

沿用 Node 26.8.2、TypeScript 6.0.3、Vue 3、Vite、`node:test` 与现有 Playwright 套件。没有新增依赖或测试框架的必要。

1. 新迁入的本地模块导入使用明确的 `.ts` 路径；`tests/*.test.mjs` 同步导入 `.ts`。Node 26 已可直接运行可擦除的 TS，本仓库其他测试也采用这种方式。
2. 类型使用 `import type`，不写 enum、namespace 或参数属性等需要额外转换的语法。保留 `allowImportingTsExtensions` 与 `noEmit`；浏览器继续交给 Vite 构建。
3. 不开启 `allowJs` 作为最终交付方案，不降低 `strict`，不新加 `@ts-ignore`／`@ts-nocheck`。`unknown` 用于真实外部边界，不能拿它替代已知内部结构；必要断言须能指向已验证的不变量。
4. 不在同一轮全面开启 `noUncheckedIndexedAccess`／`exactOptionalPropertyTypes` 等额外开关；它们会扩大到已有 TS 代码，应在存在具体需求时单独评估。
5. 一次只替换一个实现及其声明、导入和必要验证。每个阶段完成再进入下一阶段；不一次改名全部文件后长期保持主工作区报错。
6. 不把当前 `.d.ts` 机械粘贴成最终答案；它们是调用契约参考，函数体和业务验证才是校核依据。
