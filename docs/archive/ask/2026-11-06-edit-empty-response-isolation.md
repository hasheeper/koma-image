# EDIT 中 ASK 空响应的分组隔离

日期：2026-11-06。范围：用户授权对现场失败请求进行分组隔离；使用原连接的 OpenAI Chat 兼容推理接口，不执行返回的工具，不生图，不写入会话、画板、蒙版或 Photopea。

## 结论

同一份完整 EDIT 请求改为非流式返回时，渠道明确返回 `finish_reason: content_filter`；对应流式请求只返回 14 字节的 `data: [DONE]\n\n`，没有正文、工具调用或结束原因。该现场存在内容过滤，且流式返回未保留过滤原因。不能将其归为前端显示截断、六次工具预算耗尽或已经确认的上下文长度上限。

本地每轮同时发送 IMAGE 与 EDIT 完整状态。严格保持原编码、仅移除额外的 `workspace_state.image` 后，本次取得正常正文；仅移除 EDIT 能力或 Director 状态仍为空。双工作区状态的冗余是明确存在的实现问题，但本次单次成功不足以确定唯一触发字段或保证后续不再过滤。过滤可能发生在渠道或模型侧，当前响应没有进一步说明。

## 方法

- 固定同一份已有失败请求，模型、连接、历史、图片、工具定义及用户问题不变；不把测试输出追加进后续请求。
- 基线序列化请求为 203,955 字节；校验请求摘要，确保基线与导出的原请求逐字节一致。
- 字段隔离只改最后一条消息中的 `<workspace_state>`，复用项目 `stateBlock` 保留 `<` 的 `\u003c` 转义；无修改重建与原文逐字节一致。
- 各字段隔离组的工具、系统和历史前缀摘要一致。非流式组仅将 `stream` 改为 `false` 并移除流式专用的 `stream_options`；禁用工具组仅增加 `tool_choice: none`。
- 正常读取到结束，不执行模型返回工具；结果仅保存 HTTP 状态、字节、事件数、正文字符数、工具片段数、结束机器码、耗时及请求摘要，不保存凭据、地址或模型隐藏推理。

## 排除的探索结果

首轮七个删字段／极简实验使用普通 `JSON.stringify` 重组状态，意外还原了 `<` 的转义，改变了第二个变量；这些组不用于字段因果判断。发现后改用项目原序列化函数重跑有效对照。两次完整基线没有重组，仍有效。探索中相同极简请求还曾出现一次空流、一次正常回答，说明不能凭一次成功宣称稳定修复。

## 收口与后续

- 此轮仅诊断并更新记录，正式 ASK 状态、协议与提示词保持原实现；临时诊断页及其中的请求副本在结束后删除，原页面与 Photopea 内容保留。
