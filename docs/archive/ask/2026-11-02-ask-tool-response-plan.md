# ASK 工具正文模式：极简适配方案

日期：2026-11-02。状态：已实施，默认关闭；真实供应商兼容仍需逐项验证。

本方案按用户确认的「入口拆信封」原则重写。`submit_response({ content })` 只是一种输出传输格式，在接收边界转成普通正文。当前运行规则见 [ASK 运行契约](../../ask/runtime.md#工具正文模式)。

## 1. 一个开关

设置 → ASK → 创作中增加「工具正文模式」，复用已有开关样式；不依赖「自由创作」开关。

- 配置：`responseMode: "text" | "tool"`，默认 `"text"`；缺失或非法值按关闭读取。
- 沿用现有 ASK 偏好保存、同步与备份路径，不另建存储。
- 每次发送读取并冻结开关，切换不影响在途响应；显式重试采用当时配置。
- 开启后仅增加一个工具定义和一句引导词，不强制 `tool_choice`，不新增 `strict` 或 `response_format`。
- 命名、压缩和图像请求不挂载这个信封；不按模型名称自动启用。

工具参数示意：

```js
submit_response({ content: "完整的 Markdown 正文……" })
```

引导词：

> 最终回复正文请通过 submit_response 的 content 提交，也可与查询或草稿工具在同一响应中提供说明。

## 2. 在入口拆信封

```text
模型响应 → 协议适配器识别 submit_response
         → 增量解码顶层 content 字符串 → codec 还原
         → 普通 text 事件 → 既有 UI 与 assistant text 历史
```

适配器只向 provider 暴露临时的信封文本事件。provider 将它转成现有 `text` 事件；runner 按原流程保存为标准 assistant 文本。

`submit_response` 不进入业务工具注册表，不消耗业务工具次数，不生成工具卡、待确认卡或虚拟回执，也不作为工具调用写入上下文。其成功结束无需额外请求模型解释结果。

**下列文件不作任何修改：** `session.ts`、`favorites.ts`、`conversations.ts`、`compact/ledger.ts` 和 `get_turn` 所在的 `compact/archive.ts`。收藏、压缩、召回、开关切换及跨协议回放直接复用普通文本路径。

## 3. 宽容双轨接收

| 模型返回 | 接收行为 |
| --- | --- |
| 只有 `submit_response` | 解包正文，正常结束 |
| 只有普通文本 | 作为有效正文成功接收，不报“未遵循模式” |
| 正文信封 + `propose_draft` | 正文作为说明，草稿照常处理；已有正文就不补说明请求 |
| 正文信封 + 只读工具 | 展示说明，照常执行查询并继续原工具循环 |
| 普通文本 + 正文信封 | 优先采用信封正文；相同内容只展示一次 |
| 空白或非字符串信封 + 普通文本 | 使用普通文本，不因无用信封阻断回复 |
| 多个正文信封 | 使用第一份非空正文，不制造混合或重复终结错误 |

为实现去重而不改 UI 的文本状态，开启模式时先暂存同次响应的普通文本；信封正文仍增量显示。没有可用信封时，在响应结束时显示暂存文本；断流时也尽量保留已收到的普通文本。关闭模式时普通正文保持原流式显示。

模型继续直接回答不会触发重试或提示错误。真实网络错误、拒绝、完全空回复和取消仍按原规则处理，不自动续写或重发。token 长度截断沿用普通正文的截断标记，不要求补齐 JSON 后才能显示已收到的文字。

## 4. 双协议适配

| 环节 | OpenAI Chat 兼容 | Anthropic Messages |
| --- | --- | --- |
| 定义 | `tools[].function.parameters` | `tools[].input_schema` |
| 参数增量 | `delta.tool_calls[].function.arguments` | `input_json_delta.partial_json` |
| 调用关联 | 沿用 index／id 归并，工具名到齐后处理已缓冲参数 | 沿用 content block index |
| 完整对象 | 兼容直接返回已解析的 arguments 对象 | 兼容 `tool_use.input` 直接带正文 |
| 正文输出 | 转为普通 text；不保留信封调用 | 转为普通 text；不保留信封调用 |

公共增量解码器只读取顶层 `content` 字符串，处理引号、反斜杠、换行、Unicode 转义与跨分片代理对，不把嵌套同名字段或其他工具参数当正文。先解 JSON 字符串，再走现有 codec，避免分片中显示代号或重复还原。

不引入额外字段白名单、终结冲突检查、参数大小门槛或供应商能力猜测。只在结束时返回完整参数的渠道仍能使用，但正文只能在末尾显示。工具化不提高内容质量或输出上限；当前 Anthropic 普通 ASK 的 4096 tokens 上限保持不变。

## 5. 代码落点

1. **设置**：`settings.ts` 和 `AskSection.vue` 增加字段与开关。
2. **解码**：新增 `response-stream.ts`，承载轻量增量解码和仅适配层使用的事件类型。
3. **接收边界**：`adapters/*` 解信封，`provider.ts` 负责双轨选择、codec 与普通文本输出。
4. **请求入口**：`runner.ts` 和 `prompts/response.ts` 挂载工具与简短引导；`service.ts` 仅增加一行，将现有设置值传给 runner。

不修改公共消息结构、下游存储、历史读取、压缩、草稿 Schema 或 UI 正文组件。必要测试与文档随变更维护。

## 6. 验收范围

- 两协议：纯信封、纯普通文本、重复正文、不同前言、空信封、完整参数对象及迟到工具名。
- 流式：中文、引号、换行、反斜杠、代码块、Emoji、Unicode 转义与 codec 跨片段；完整响应到达前能看到正文。
- 工具混用：正文与草稿／查询同返，业务工具照常执行，草稿不多请求一次说明。
- 历史：只保留标准 assistant 文本与实际业务工具；收藏刷新、关闭模式、切换协议后可继续对话，原 `replyText`／`get_turn` 能直接读取。
- 异常：长度截断保留文字和原标记，真实断流仍失败且不自动重试。
- 设置：默认关闭、保存与重新读取、开关的实际请求效果。

验证使用合成内容和模拟服务，不调用真实收费模型。运行 `npm run check`、相关 ASK 浏览器用例及设置样式检查；真实渠道支持程度不由本地模拟结果推断。
