# 版本演进：参数归组与多工作区状态重整

日期：2026-11-11。状态：**保留为修改前问题证据；目标方案已由后续规划替代。**

后续用户框架已收敛为[IMAGE 主干、事后立为阶段与工坊交付](2026-11-11-evolution-image-workshops-plan.md)。本文的“三工作区独立实时游标”及“用户预先新建空框”不再作为实施目标；源码现状与错误成因仍可用于核对。后续两项决定——只提拔选中图、工坊结单后原板续交——统一维护在新规划中。

本文梳理用户遇到的问题、现有实现的职责混用及已确认的目标规则，作为恢复实施前的核对稿。现行专题入口是[版本演进](../../workspaces/recipe-retrospect.md)。工作树中上一轮已产生的源码修改保留，尚未完成的收口不视为已经交付；本次不继续修改源码、不重新运行测试、不 build，也不更新用户正在使用的页面。

## 1. 先明确问题是什么

这次需要重整的是三件相互关联、但应分别处理的事情：

1. **记录变化与划分阶段分开。** 每张图片应保留完整真实参数；出现参数差异，不等于必须新增一个 `vN`。用户手动改词、调重绘幅度或修改蒙版，默认仍属于当前阶段。
2. **一棵树与各工作区的活动状态分开。** 同一主题可以在 IMAGE、EDIT、CHAT 中继续创作，三个工作区的分支可以同时保持激活。交接不会把整棵树的所有权搬走，也不会锁死来源工作区。
3. **查看、恢复和比较各按自己的依据执行。** 查看哪个节点不等于正在从哪个节点生成；恢复应按所选具体样本的原生工作区分派；跨区内容属于交接关系，不能将 NAI 标签与 CHAT 操作说明当成同一段提示词的删改。

因此，单纯放宽“参数相似度”不能解决问题；单纯增加三个工作区的开关也不能解决恢复和 Diff 的语义错误。

## 2. 现状证据的三个层次

| 层次 | 可以确认的事实 | 不能据此声称的事情 |
| --- | --- | --- |
| 用户正在使用的页面 | 出现过重绘微调反复拆节点、转到 CHAT 后不能恢复 IMAGE、跨区提示词整段红绿替换 | 不能仅凭当前源码判断该页面已经使用修复后的资源 |
| 原有逻辑及 Git 基线 | 演进记录只有一组画板归属与游标；交接会改写这组归属；归组依赖有效配方签名；恢复分派依赖树的目标工作区 | Git 基线不等于用户当前页面逐字对应的资源快照，本地还有其他尚未提交的功能 |
| 当前本地在改源码 | 已加入分工作区跟踪、显式待生成目标、按样本恢复和跨区原文展示等调整 | 局部验证不等于整体方案已收口，也不等于已 build、发布或修复用户现有内存树 |

上一轮已做过部分单元与模拟浏览器验证；本轮暂停后不追加验证，也不把此前结果作为本次重整稿全部规则的验收结论。

## 3. 必须区分的对象

| 对象 | 含义 | 与其他对象的关系 |
| --- | --- | --- |
| 图片样本 | 某次真实生成或编辑结果及其原始输入快照 | 一个阶段可包含多张样本，每张配方都应独立读取 |
| 候选配方组 | ASK 读取历史时，程序按有效配方折叠的证据集合 | 用于减少重复资料，不直接决定最终的 `vN` 划分 |
| 演进阶段 `vN` | 用户或 ASK 明确组织的一次创作方向／阶段 | 允许多张配方略有不同的样本，不能要求组内参数完全相等 |
| 实际输入底图 | 某次 EDIT／CHAT 操作真正使用的图片 | 属于事实证据；它可能一直是早期原图 |
| 当前阶段与待生成目标 | 下一张结果应进入哪个已有阶段，或兑现哪个新占位 | 不应仅靠实际底图或配方签名反推 |
| 工作区跟踪 | 当前主题在某个具体 IMAGE 画板、EDIT 画板或 CHAT 会话上的续接状态 | 同树内各路独立；页面导航只决定当前查看哪一路 |
| A/B 查看选择 | 用户正在比较的节点与具体样本 | 不写表单、不改变底图、不移动生成目标 |

尤其要区分三种“相同”：候选折叠用的**有效配方相同**、恢复校验用的**具体原始快照匹配**、生成归属用的**同一阶段**。它们不能共用一个判定来决定所有行为。

## 4. 三个工作区实际记录什么

| 内容 | IMAGE | EDIT | CHAT |
| --- | --- | --- | --- |
| 词文 | 原始基础正负词、原始角色槽 | 当次操作原始说明；所用模型支持时包括负向与角色 | 当轮原始需求及实际选入的历史文字 |
| 生成参数 | 模型、尺寸、采样器、步数、Guidance、相关预设与参考配置等 | 实际操作生效的模型、模式、重绘强度、噪声、尺寸、工具参数等 | 当轮模型与实际选项，如尺寸、质量等 |
| 图片来源 | 绘图配方中的参考资产配置 | 实际底图、参考图、来源版本 | 明确底图与参考图、所属会话／轮次／版本／资产 |
| 蒙版与局部处理 | 按实际操作记录，不把其他工作区字段补进来 | 已冻结蒙版指纹、范围、覆盖率，以及外扩、羽化、色彩对齐、聚焦等生效设置 | 按实际发送或回贴操作记录区域批注／蒙版等信息 |
| 操作类型 | 绘图生成 | 图生图、重绘、放大、Director、Photopea、回贴／融合等 | 对话生成及实际合成来源 |

记录层与展示层遵守以下边界：

- 记录保留真实原文与当次生效值，不用当前表单补造旧记录。
- 空值、未记录、已知没有蒙版应分开；蒙版摘要不能替代原蒙版像素，也不意味着可以完整恢复当时的蒙版。
- 停用角色槽、正负词均为空白的角色槽只在候选与 Diff 投影中忽略；完整恢复仍使用原始记录，不删除源数据。
- Seed／批次信息不应成为阶段拆分依据；恢复和结果参数是否包含这些值，沿用原有记录与各工作区恢复契约。
- 不同模型可能共用字段名却使用不同含义；不能因都叫 `prompt`、`strength` 或 `quality` 就直接互相解释。

## 5. 当前问题与形成原因

| 编号 | 问题 | 现状与原因 | 重整方向 |
| --- | --- | --- | --- |
| P01 | 微调一下重绘幅度或蒙版就长出新节点 | 原有落图逻辑把有效配方签名变化用于阶段拆分；精确记录变化的能力变成了过度拆分 | 保留变化记录，阶段归属改由明确的生成目标决定 |
| P02 | 进入 CHAT 后 IMAGE 不再跟踪 | 原有 `transfer` 改写整树唯一 `boardId/cursor`；来源工作区不再匹配活动树 | 各路独立关联同树，交接只建立／调整目标路 |
| P03 | 选中 IMAGE 旧图却走 CHAT 恢复 | 原有恢复根据整树最后绑定的目标区分派，而不是根据所选样本 | 具体样本决定原生工作区与恢复路径，成功后只调整对应一路 |
| P04 | NAI 配方整段被“替换”为 CHAT 海报合成指令 | 原有 Diff 把共享数据容器中的两个 `prompt` 当成同语义字段 | 跨区展示交接与双方原文；禁止生成整段红绿替换的误导 |
| P05 | EDIT 的底图、当前阶段和下一次分支关系容易混用 | EDIT 可继续使用 v1 原图，结果却已经在 v2 阶段；当前在改源码仍结合 `cursor`、`destination` 表达这两件事，连线来源仍取实际输入基底 | 明确阶段续接与像素来源的不同职责，见第 10 节待审边界 |
| P06 | 各路草稿撤销可能互相影响 | 当前在改源码已给变更附加工作区目标，但撤销预检的模拟游标仍只以整树 ID 为键 | 撤销／重做／预检都必须按树与具体工作区目标核对；本轮只登记问题 |
| P07 | 顶层“当前工作区”可能盖过其他路状态 | 当前在改源码同时保留顶层游标投影与 `trackings`；`get(id, target)` 在目标未绑定时会返回整树当前投影 | 需逐项核对 UI、工具读取、恢复和生成入口是否明确检查目标关联，不能把回退投影误当作该路已经激活 |
| P08 | 文档同时存在相反描述 | 专题前部仍写“基底后方总有空框、成功后继续产生占位”，后部已写“明确目标才出现、转实后消失”；部分入口已将未收口修复写为完成 | 以本次审阅稿区分现状与目标，后续方案通过并收口后统一维护正文 |

当前在改源码已经处理了 P01–P04 的部分主路径，但 P05–P08 说明这次问题不能只按几个报错点分别打补丁。暂停期间保留代码，不据此宣称整体已经完成。

## 6. 用户已确认的阶段规则

| 行为 | 是否准备新阶段 | 下一张成功图的归属 |
| --- | --- | --- |
| 用户手动改词、调参数、改重绘强度、蒙版大小或边缘设置 | 默认不准备；不再判断修改幅度大小 | 当前工作区当前阶段，保存该图真实配方 |
| 用户明确“新建节点” | 准备独立可拖动的空白占位 | 填入该占位，保持其位置 |
| ASK 仅分析、看图、读取参数、整理已有历史 | 不因工具调用本身准备 | 当前归属不变 |
| ASK 提议新改法但尚未确认 | 不写画板、不切换生成目标 | 等待用户确认 |
| 用户确认 ASK 的有效配方／操作修改草稿 | 为本次改法准备待生成目标；已有尚未兑现的同一目标应复用 | 首张成功图填入该目标；用户期间顺手微调也兑现它 |
| 载入 IMAGE 完整预设分支 | 使用该预设自身的待生成节点 | 首张成功图原地转实，包括载入后又做微调的情况 |
| 将树中图片显式送到另一个工作区继续处理 | 目标区准备新阶段，来源区保持激活 | 目标区第一张成功结果进入该阶段 |
| 只点击 IMAGE／EDIT／CHAT 导航 | 不准备、不结束跟踪 | 各路原有目标保持 |
| 显式恢复旧样本 | 回到该样本所属工作区并调整该路基底 | 恢复本身不等于请求新增阶段；若要另开尝试，由新建节点或 ASK 修改明确表达 |
| 失败／取消且没有成功图 | 不兑现目标 | 占位保留以供用户再次生成 |
| 首图成功后继续手动微调或续抽 | 不自动追加下一个空框 | 继续进入已经兑现的阶段 |

纯文件、任务板或命名等草稿不应因“由 ASK 发出”就创建图像占位。“ASK 新改法”指经过确认、实际改变图像创作输入的草稿。

普通空白占位与完整预设分支也需要分清：前者表示本工作区下一张图的落点；后者在树中已经保存了一套完整候选配方，可以在生成前审阅 Diff。不能为了共用虚线外观，混用两者的配方、载入与删除语义。

## 7. 多工作区：同树同时激活，各路各自续接

一个例子是：IMAGE 的 v2 同时送入 EDIT 修眼睛、送入 CHAT 合成 Logo。此后 IMAGE 仍可继续调整构图，EDIT 仍可修局部，CHAT 仍可调整排版；三路结果都进入同一主题树。

每一路至少需要独立表达：关联的具体画板／会话、当前阶段、实际创作基底、待生成目标及其位置、跟踪有效性。树共享节点、连线、批注、定稿与本页生命周期。

- 当前显示 CHAT，不代表 IMAGE／EDIT 变为失效。
- 后台落图只更新发起那一路，不把另一工作区的游标或占位挪走。
- 从 IMAGE 旧样本恢复后，CHAT 原有阶段和待生成目标继续保留；从 CHAT 旧样本恢复时也同理。
- 同一工作区切换／新建具体画板或 CHAT 会话，沿用既有换题断代边界，只处理该路关联；这与三个工作区之间切导航不同。
- 显式解除整树跟踪或设为定稿结束整树；普通收藏、关闭弹窗、收起 ASK 不结束。
- “同时激活”是跟踪关系同时有效，不改变全应用默认并发为 1，也不自动生图或自动发送 CHAT。

同树可以有多个跨区阶段，但一个阶段内的样本应使用明确的原生工作区契约，不能把 IMAGE 与 CHAT 混装到同一个 `vN` 再选择性解释字段。

## 8. Diff 的边界

| 比较场景 | 应呈现什么 | 需要避免什么 |
| --- | --- | --- |
| IMAGE → IMAGE，输入含义兼容 | 原始词文红绿 Diff、有效角色与参数变化 | 按差异多少自动拆阶段 |
| EDIT → EDIT，操作与输入含义兼容 | 原始说明及适用字段 Diff，另列底图、蒙版、操作参数变化 | 把蒙版指纹作为面向用户的主要描述；把休眠参数当作实际变更 |
| CHAT → CHAT，输入含义兼容 | 当轮需求变化，分别列历史文字、底图／参考图与选项变化 | 把整段拼接后的发送内容都当作本轮手写 Prompt |
| IMAGE ↔ EDIT、IMAGE ↔ CHAT、EDIT ↔ CHAT | 工作区交接方向、具体来源样本、双方各自完整原始输入与参数 | 将 A 的全部词文标红、B 的全部指令标绿，暗示它们互为替换 |
| 同一工作区切换到不同输入契约／工具 | 模型或操作变化事实；是否能做词级比较需进一步判定 | 只因 `workspace` 相同就认定语法和参数完全可比 |
| 旧记录缺字段 | 标记未记录，展示仍然可确认的信息 | 用当前默认值或另一工作区的字段补齐历史 |

用户提供的案例应显示为：**IMAGE 插画生成 → CHAT Logo 合成**。左侧保留 NAI 的画风、角色与构图配方，右侧保留“第一张为底图、第二张为 Logo 参考”的合成要求，并列明来源关系；这不是删除整套 NAI 配方后改写成一篇自然语言提示词。

当前在改源码已经加入跨 `workspace` 的展示边界；同区换模型／工具的兼容性尚未完整定义，不能把“仅同区比较”当作最终充分条件。

## 9. 恢复的边界

| 选中的具体样本 | 恢复行为 | 限制与区别 |
| --- | --- | --- |
| IMAGE | 恢复原始绘图配置，按原生绘图写入路径核验，定位正确 IMAGE 画板 | 是否仍有原图与是否仍有完整配方是两回事；不可把 CHAT 说明写进绘图表单 |
| EDIT | 按具体编辑样本回到对应 EDIT 画板、恢复支持的配置与底图关系 | 不把蒙版摘要当作历史蒙版回放；同尺寸沿用当前蒙版，跨尺寸遵守现有清空规则 |
| CHAT | 定位具体会话／轮次／版本／图片，准备以它继续分支 | 恢复图片起点不等于恢复整段历史对话或覆盖当前输入；需要新需求时另走草稿 |

分派依据是**所选样本的原始输入与稳定身份**，不是整棵树最后打开过哪个工作区，也不是图片后来在哪个工作区出现过。收藏别名与跨区导入不能改写原配方的语法归属。

恢复成功后只更新对应一路；失败保留原配置与跟踪状态。原记录删除、原板不可用、当前模型不支持历史参数等情况，应分别呈现实际原因，不能统一误报成“当前树属于 CHAT”。

## 10. 恢复实施前仍需收口的细节

以下是需要在方案中统一的边界，并非本轮开始修改的授权：

1. **阶段连线与实际底图的关系。** EDIT 在 v2 阶段继续用 v1 原图，新建 v3 时，阶段脉络与像素来源可能不同。建议用演进连线表达选择的阶段关系，用操作来源明确记录“实际底图仍是 v1”；显式从 v1 回退分叉时再以 v1 作为阶段父节点。当前在改源码仍由实际输入底图推导新增连线，此处需先统一再实施。
2. **同区换模型／工具的 Diff 兼容范围。** 例如 EDIT 中 NAI 重绘换成通用图像模型编辑，不能仅凭同在 EDIT 就比较整段语法。建议按已知输入契约和字段含义决定可比部分，信息不足时展示各自原文；不按模型名字硬猜。
3. **三个活动目标如何显示。** 当前在改界面主要显示当前工作区的普通占位，其他路目标在内存保留。是否同屏显示三路占位、如何标明各区起点，尚未定稿；“三路都激活”不能只靠一个会随页面变化的图钉来暗示。
4. **容量与普通占位。** 已批准的上限保持：总节点 80，IMAGE 完整预设每轮成功新建最多 4、每树未生成预设最多 16。普通工作区占位不等同于完整预设；多路同时等待生成时如何预留总节点容量，应在实现中统一，不能误套每树 16 的口径。

## 11. 后续收口顺序与场景核对

重新开始实施前，先确认第 10 节的统一表达，再按以下依赖顺序修改；本轮停在文档审阅：

1. 统一“样本、阶段、实际底图、工作区跟踪、待生成目标”的职责。
2. 明确三路生成、交接、恢复、解除与晚到结果的状态规则。
3. 确认参数／词文的可比边界，再整理 Diff 与原生恢复入口。
4. 将草稿确认、撤销、重做与多步预检纳入同一套工作区作用域。
5. 核对画布占位、阶段连线、A/B 与 ASK 所见状态，最后同步现行文档及发布说明。

后续至少应覆盖这些实战场景：

| 场景 | 核对结果 |
| --- | --- |
| EDIT 重绘强度从 0.45 调至 0.50，再改蒙版后生成 | 留在同阶段，各样本参数与蒙版变化可查 |
| ASK 确认新改法后，用户又补几个词再生成 | 首图填入已准备的目标，保持拖动位置，不留下空壳 |
| IMAGE 同时交接 EDIT 与 CHAT，然后三路轮流生成 | 来源与两条目标路都继续有效，各自归属正确 |
| 在 CHAT 路选中早期 IMAGE 样本恢复 | 回到 IMAGE 原生表单；CHAT 与 EDIT 的状态保留 |
| NAI 插画与 CHAT Logo 合成并排查看 | 展示交接与双方原文，没有整段伪替换 |
| EDIT 保持 v1 底图，先产生 v2，再明确创建下一阶段 | 阶段关系和实际底图分别准确表达，不因底图未变丢失阶段 |
| 同树各区先后确认草稿，再连续撤销／重做 | 按各自目标核验，没有跨区游标误冲突或重复提交 |
| 一路生成未完成时切到另一区继续查看或恢复 | 晚到结果归原发起目标，不抢另一工作区游标 |
| 关闭演进、普通收藏、最后显式设为定稿 | 前两者保持跟踪，定稿结束整树 |

这些是后续验证清单，不代表本轮已实施或已验收。既有树的碎节点也不在本轮自动合并；先保留真实样本、用户排布与批注，再讨论是否由 ASK 重新归纳。
