## 接入方式

`src/services/application.ts` 在 `src/main.ts` 中创建一次，由 Vue 的 injection 提供给工作区；服务实例、数据库、凭据和取消句柄均不进入 reactive。工作区切换不会重新初始化数据库或释放任务。

- 读取能力：`services.gateway(connectionId)` 提供目录、预报价和额度。
- 生成能力：`services.runTask(spec, callback)` 给整个批次／对话轮次／编辑操作持锁。回调中的 `task.gateway(id).execute(payload, consume, options)` 执行重报和提交；必须等待 `consume` 完成图片解码／校验及归属处理后退出任务。回调退出后不能继续用它提交。失败由调用方按原 UI 展示；忙时返回 `busy`，维护时返回 `maintenance`。
- 参数必须是提交时的快照。任务 signal 自动传入网关；切换工作区不取消，显式取消才中止。原图等大资源由工作区资源服务持有，不放进 Vue 深层状态。
- 保存使用 `services.data.write(...)` 包住 IndexedDB／偏好写入。数据库事务接口仅是底层能力，不应绕过应用数据租约直接写入。
- 持有延迟保存或缓存的模块通过 `data.register({ flush, reload })` 注册。`flush` 清理定时器并使用收到的 writer 落盘；`reload` 在恢复准入前读取新数据。刷新失败保持冻结，防止旧缓存覆盖导入内容。
- 导入通过 `data.import(...)`，导出通过 `data.export(...)`。自身运行任务会阻止导入，但不会被自动取消；其他标签页也会阻止独占导入。导入成功、部分失败及取锁失败后都重新取得共享租约并刷新缓存。落盘失败时保留原租约、不开始导入。

任务槽位按 1..N 编号，当前容量固定为 1，没有用户配置入口。`ReservationPort` 仅定义未来预占的提交前／已确认／计费未明生命周期接口，应用没有接入任何账本或扣减逻辑；多标签预占及真实自定义并发仍未启用。`acknowledged` 只表示响应已消费成功，不等于已经核实最终扣费；将来接入账本时仍需实际结算数据。

## 配置与秘密边界

正式配置没有默认连接。没有 URL 或没有解锁的 Key 时，获取连接上下文立即失败，不请求上游。URL 仅接受 HTTPS 或本机 HTTP，拒绝 URL 内嵌凭据、查询参数及片段；请求不携带站点 cookie、不跟随重定向，不打印 URL 或 Key。

普通请求使用 Bearer；额度统计的专用查询认证仅由 Profile 明确声明，使用 no-referrer。这是协议兼容要求，直连时浏览器仍能查看自己配置的请求。源代码中没有渠道身份判断。合法模型供应商与协议字段保留。

Key 暂由内存凭据入口提供给服务，空输入不会覆盖已有 Key；新版本 Key、配置变化、锁定或连接移除会使旧上下文失效。目录缓存按连接／配置／凭据版本隔离，不使用原始 Key 作缓存键。连接配置损坏时内存回到空配置，失效上下文不能继续通信，不自动改写磁盘。

M3 已接入原 PBKDF2 210000／AES-GCM vault、session 模式和跨标签解锁流程。M2 当时没有凭据输入表单，也未新增明文持久化 Key 的方式。[M7](release-acceptance.md) 已实现本地环境变量代理与只读设置；沿用 `apiBase(document.baseURI)` 的根路径／子路径解析，不主动探测服务、不自动回退地址。

## 数据与备份边界

应用启动只打开 `koma-image-favorites`（favorites）、`koma-chat`（conversations／assets）、`koma-handoff`（items）。数据库 version=1 与备份 envelope version=2 是两个独立版本号。普通历史仍只属于工作区内存，M2 不写历史。

备份偏好使用 drawing、routing、chatSettings、currentConversation、chatRail、tagCart、tagCategories 逻辑字段。收集时只读取白名单，不遍历存储；Key、派生密钥、普通历史、编辑会话与交接均不在导出范围。只接受新版 Koma envelope；不识别或转换其他格式。

本阶段建立备份元数据契约，**尚未实现 ZIP 文件读写、图片 CRC／哈希校验、合并去重及冲突副本导入**。这些属于 M3 普通备份子页，必须在实际写入前完成校验。保留了原 ZIP32 的 4GB、60000 条目、64MB 目录、32MB manifest、128MB 单图片等限制供下一阶段使用。

旧数据迁移已取消。没有旧库检测／删除、过渡桥、转换脚本、迁移 UI 或发布前置条件。

## P3.1 Profile 泛化

2026-10-19，为接入公开官方协议做的纯重构，标准 Profile 的行为不变：

- **注册表。** `profileFor` 从登记表查找，未知 ID 和原型属性名都拒绝；连接校验、备份恢复、网关和连接诊断都走它。P3.1 交付时只登记标准 Profile，后续已加入三种原生协议。
- **能力可声明。**
  - `costCeiling` 改为可选；
  - `catalog.requireCostCeiling` 和 `auth.statsQueryKey` 由协议声明；
  - 路径表允许缺项，请求未声明的路径时报「连接不支持本次操作」；
  - 原生入口的附加请求头改为 `transport.nativeHeaders`，本地代理同样读取它。
- **无报价执行。** 只有既不支持报价、也没声明费用上限的协议，才走这一支：不报价，不带上限字段，不预占，返回的 `quote` 为 null。声明了费用上限却不支持报价时，仍然拒绝执行（`QuoteUnsupported`）。P3.1 当时尚无实际协议使用，后续三种原生协议已接入这一分支。
- **额度按来源计算。** `normalizeQuota` 记录状态来自哪个连接的 Profile，`quotaPolicy` 的阈值和钱包的低额度、告急比例都取自它，不再默认使用标准 Profile。对话和编辑从报价里带回的额度同样记录来源。

检查：`npm run check`（50 项单元）和 7 组浏览器测试（36 项）通过，原有断言未改。新增单元测试覆盖注册表、未声明路径、无报价执行（含工具路线和预占跳过）、有报价但无上限、空原生请求头、目录不要求上限，以及额度阈值和钱包等级随 Profile 变化。
